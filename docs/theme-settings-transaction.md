# Theme settings transaction (direct-edition Flux)

`LauncherSettingsStore.prepareOmarchyTheme(payload)` snapshots and validates a canonical palette without touching disk. Its one-use `commit(authority)` serializes with `read`, `write`, `updateRaw`, Omarchy Link peer updates, and legacy writes on **the same store instance monitor**. At commit it reads the latest `settings.json`, changes only `omarchyTheme`, stages JSON in a same-directory temporary file, syncs its bytes, checks the caller's independent nonblocking authority token, renames, then syncs the parent directory. It removes the temp on denial or ordinary I/O failure. A denied check or failed pre-rename stage returns `NOT_COMMITTED`; a successful rename and directory sync returns `COMMITTED`; a directory-sync failure after rename returns `INDETERMINATE` (the new pathname can already be visible). The injected `ThemeTransactionIo` must actually sync staged bytes and atomically replace the target; a fake implementation does not supply durability.

This is a **practical bounded window, not atomic revocation**. Revoking while stage I/O is blocked can promptly flip an independent token without waiting for the store monitor, and the later check prevents replacement. Revoking after that check, including during a blocked rename, cannot prevent that rename. A blocked staging/rename/sync holds the store monitor, so other settings writers wait; do not move the stage outside the monitor and claim all-writer serialization. The monitor only serializes one store instance in one process; external writers or another instance are outside this contract. Temp cleanup is best effort if deletion itself fails.

`write(LauncherSettings)` now preserves the latest persisted `omarchyTheme` at the serialized write boundary, even if a full-model UI snapshot was captured before a Flux commit. Explicit `updateOmarchyTheme` and `updateTheme` remain able to change the theme. Other unrelated stale full-model fields are not conflict-resolved. Omarchy Link's `updatePeer` uses the raw merge path.

The direct edition advertises catalog reception and selection, and `FluxThemeFlow` passes a nonblocking exact-session/generation authority check into the prepared transaction. Applies are globally serialized; a stale session cannot publish UI state or finish a successful local selection ACK. An old rename that was already entered may still publish a **transient stale disk theme** after revocation; when that filesystem operation returns, the flow schedules the latest live desired catalog again even without a new packet. A permanently blocked stage/rename/sync prevents both reconciliation and subsequent store writes. A post-rename sync failure is indeterminate and not reported as a successful local apply. These are practical eventual-newest-wins conditions, **not** strict atomic revocation or bounded progress guarantees. Play neither advertises nor receives Flux themes. The Flux theme catalog contains palettes; the independently negotiated wallpaper extension carries originals and gallery previews. Physical phone/desktop theme and wallpaper delivery was verified on October 2, 2026 against the deployed integration baseline; newer upstream compatibility requires separate validation.
